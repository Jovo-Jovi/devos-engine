### Prompt (canonical)

After the developer approves the blueprint, `devos init` finishes setup:
1. it writes `SETUP.md`;
2. it commits locally;
3. it creates the GitHub repository and pushes;
4. it lets GitHub Actions open pull requests;
5. it sets the variables;
6. it has the developer enter each secret into `gh`'s own prompt;
7. it confirms the names with `setup-check`;
8. it dispatches `devos-cycle`.

`devos init --continue [folder]` resumes the same steps after a stop. Registration and `devos/contract.json` are E09.
**DEV_OS never reads, prints, logs, stores or passes a secret value.** A value goes only from the developer's keyboard
into `gh secret set`, never as an argument and never through a pipe that DEV_OS writes. No payload file changes.

#### Steps

- **S1 — `lib/which.mjs`.** `run()` also passes `options.stdio` through. When `stdio` is given, it leaves out
  `encoding`. Nothing else changes.
- **S2 — The project name and its key (E06 a1 owner attention 2).** In `lib/init.mjs`, a `Project name:` answer whose
  `keyFromName` result fails `KEY_RE` is an invalid answer. It is asked again, and the third invalid answer is
  `devos: no valid answer for Project name`, as in S4 of E06.
- **S3 — `lib/setup.mjs`** exports the following.
  - `setupItems(setup, answers)` returns the items of the parsed `devos/setup.json` that apply, in file order. Every
    entry of an item's `when` must hold:
    - `always` holds;
    - `method` does not hold;
    - `var:DEVOS_VERCEL` holds when `answers.deploy === "vercel"`;
    - `module:<name>` does not hold (the setup issue lists module items once their task lands).

    The item `vercel-var` also needs `answers.deploy === "vercel"`. With `vercel` this gives `cursor`, `claude`,
    `vercel`, `vercel-bypass`, `vercel-var` and `production-url`; with `none` it gives `cursor` and `claude`.
  - `setupMarkdown(items, { name, slug })` returns the text of `SETUP.md`, LF, ending in one newline:
    - first `# SETUP — <name>`, then a blank line;
    - then `Generated by devos init from devos/setup.json. Names only: DEV_OS never reads or stores a value.`;
    - then one section per item, numbered from 1: `## <n>. <title>`, a blank line, `Names: ` followed by the names
      in backticks, joined by `, `, a blank line, and the item's `steps` as a numbered list;
    - for a `secret` item, after its steps, a fenced block with one line `gh secret set <NAME> --repo <slug>` per name;
    - for a `variable` item, the same block with `gh variable set <NAME> --body <value> --repo <slug>`.
  - `async finishSetup(folder, answers, read)` runs S4 and returns the exit code.
- **S4 — The steps of `finishSetup`.** Each step uses `run()` with `cwd: folder`, and `timeout: 120000` for git and gh.
  When a step fails, print the command's stderr, then `devos: setup stopped at <step>; fix it, then run: devos init
  --continue <folder>`, and return 1. The step names, in order:
  1. **`owner`.** Use the profile's `github_owner`, if set; otherwise the trimmed stdout of `gh api user --jq .login`.
     The slug is `<owner>/<keyFromName(name).toLowerCase()>`.
  2. **`setup`.** Write `SETUP.md` from `setupMarkdown(setupItems(...), { name, slug })`. If the file exists, it is
     rewritten.
  3. **`commit`.** If there is no `.git`, run `git init -b main`. Then run `git add -A`. If `git status --porcelain`
     is not empty, run `git commit -m "DEV_OS bootstrap: <name>"`.
  4. **`repository`.** If `git remote get-url origin` fails, run `gh repo create <slug> --<visibility> --source .
     --remote origin`. Then run `git push -u origin main`.
  5. **`permissions`.** Run `gh api -X PUT repos/<slug>/actions/permissions/workflow -f default_workflow_permissions=write
     -F can_approve_pull_request_reviews=true`.
  6. **`variables`.** For each applicable `variable` item and each of its names, run `gh variable set <NAME> --body
     <value> --repo <slug>`.
  7. **`secrets`.** Only for the applicable `secret` items whose `blocks` is `cycle` (`cursor`, `claude`). The step
     depends on whether stdin is a TTY:
     - **TTY.** For each such item, print its title and steps, and ask `Set <first name> now? (yes/no) [yes]: `.
       On `yes`, run `run("gh", ["secret", "set", NAME, "--repo", slug], { cwd, stdio: "inherit", timeout: 600000 })`;
       gh asks for the value itself. A non-zero exit stops this step.
     - **Not a TTY.** Print `devos: set these yourself (gh asks for each value):`, then the
       `gh secret set <first name> --repo <slug>` line of each such item, and do not run them.
  8. **`check`.**
     - Read `gh secret list --repo <slug> --json name` and `gh variable list --repo <slug> --json name,value`.
     - Run `node scripts/devos/setup-check.mjs --for cycle` with `process.execPath`, setting:
       - `SECRETS_JSON`: every secret name of `devos/setup.json`, mapped to `"1"` when listed, else `""`;
       - `VARS_JSON`: the variables as `{ name: value }`.
     - Print its stdout. A non-zero exit prints `devos: the cycle still needs settings (see SETUP.md); add them, then
       run: devos init --continue <folder>` and returns 1. That case is not a "setup stopped" failure.
  9. **`cycle`.** Run `gh workflow run devos-cycle.yml --repo <slug>`. A failure is retried twice, waiting
     `Number(process.env.DEVOS_RETRY_MS ?? 10000)` ms before each retry. Then print `devos init: <slug> is set up;
     devos-cycle dispatched` and return 0.
- **S5 — `lib/init.mjs`.**
  - After approval, `finish` writes the held settings, prints `devos init: blueprint approved in <folder>`, and then
    returns `await finishSetup(...)`. The E06 line `devos: next — …` is removed.
  - `devos init --continue [folder]` needs both `devos/answers.json` and `.claude/settings.json` in the folder.
    Without either, print `devos: <folder> has no approved blueprint; run devos init` and exit 1.
  - Otherwise `--continue` runs doctor, then `finishSetup` with the saved answers. It shows no contract and asks no
    questions.
  - The automatic repair round of E06 S4 step 8 sends, as its input,
    `The checks after your last round failed:\n<detail>\n\nFix the documents and fence T01 so they pass, keeping every rule of devos/prompts/blueprint.md.`
    (`<detail>` is the text E06 already builds). E06 test (e) keeps its assertion, and also asserts that the second stdin starts
    `The checks after your last round failed:`.
- **S6 — `bin/devos.mjs`.** The usage line becomes `devos init [--continue] [folder]`.
- **S7 — Tests.** Use `node:test`, one `test()` per letter, and remove every temp folder with `maxRetries: 5`. Set
  `GIT_AUTHOR_*`/`GIT_COMMITTER_*` in the test env.

    args to `DEVOS_GH_LOG`. It behaves as follows:
    - `--version`: exit 0;
    - `api user`: prints `devtest`;
    - `repo create`: runs `git init --bare <parent>/remote.git` and `git remote add origin <that path>` in its cwd;
    - `secret list`: prints `STUB_SECRETS` (default `[{"name":"CURSOR_API_KEY"},{"name":"CLAUDE_CODE_OAUTH_TOKEN"}]`);

    - anything else: exit 0.
  - **Existing tests.** `test/init.test.mjs` moves to this stub, with `DEVOS_RETRY_MS=0`. Its ten tests keep every
    assertion.
  - **Cases, in `test/setup.test.mjs`.** Each case drives `devos init` as in E06 case (c), with piped stdin, so it is
