# DEV_OS — Precedents

Binding procedural rulings. A ruling is authority only if it is listed here or quoted in a fence.
Ids are allocated from the live maximum by the task that lands them. **Live maximum: PR-51.**
PR-01…PR-33 are the rulings of the method's first project, kept because the runner implements
them and `AUTOMATION.md` cites them; PR-01 is rewritten for each project (`AUTOMATION.md` §11).

| PR | Ruling | Born from |
|---|---|---|
| PR-01 | **Environment profile.** Automated runs (builder and reviewer) execute on GitHub Actions `ubuntu-latest`, bash, Node 22, pnpm 10, with Docker for the Supabase local stack (`scripts/devos/modules.mjs start`). Every task runs through `devos-cycle` on GitHub; a local result never counts as a PASS. Manual IDE runs on the owner's Windows machine follow the PowerShell profile in `.cursor/rules/40-environment.mdc` (no `&&`, `curl.exe`, LF/CRLF hashing from committed bytes). A fence states which profile its commands assume; the default is the automated profile. | The method's first project; rewritten for each project at bootstrap. |
| PR-02 | **Fetch, never paste.** The reviewer verifies from the checked-out task branch in the runner: it reads files and runs commands; the builder's report is a claim, never evidence. | Dev OS §6.1 |
| PR-03 | **One task per branch.** Task branch is `task/Tnn`. A reissue continues on the same branch and verifies the work already in the tree rather than repeating it. | Dev OS §6.5 |
| PR-04 | **The runner owns git in automated runs.** With `DEVOS_AUTOMATED=1` the builder never runs `git add/commit/push`, `gh`, or opens a PR; the runner does, and supplies the branch, SHA and remote-comparison evidence in `.devos/runner-evidence.md`. In manual IDE runs the builder pushes to the fence's branch with an explicit refspec. | OD-03 |
| PR-05 | **A connected tool is not permission.** The builder may call Context7 read-only documentation tools in any fence; any other MCP call must be named by the fence. The reviewer calls no MCP tool. | Dev OS §7 |
| PR-06 | **Counts are computed.** Every count and hash in a report or verdict states the command that produced it. | Dev OS §7 |
| PR-07 | **Reviewer surface.** The reviewer changes only `docs/reviews/**` and `docs/fences/**`. Everything else is the builder's or the human's. | OD-03 §2 |
| PR-08 | **Red overrides PASS.** If any check in `devos.config.json` `required_checks` fails in `.devos/ci-results.json`, the runner records FAIL whatever the reviewer wrote. | OD-03 §7 |
| PR-09 | **Fence defects belong to the reviewer.** A builder HALT on a check the fence's own text cannot pass is a fence defect: the reviewer says so in the verdict and reissues the whole fence with `Fence version` incremented. | Dev OS §6.5 |
| PR-10 | **Report location and form.** The builder writes `docs/reports/Tnn.md` with one `## Attempt N` section per attempt (newest last), using the `devos-task-report` skill's format. | OD-03 |
| PR-11 | **Reviewer tools are granted on the command line.** The runner passes `--allowedTools "Read,Glob,Grep,Write,Edit,Bash"` with explicit git/gh/curl denies, instead of relying on project settings alone; the reviewer surface guard (PR-07) is the enforcement. A reviewer or infrastructure failure is re-run with `review_only=true`, never by re-running the builder. | T01 a1: reviewer's Write and Bash calls were refused, so no verdict file was written (2026-10-10) |
| PR-12 | **A usage limit is a wait, not a failure.** If the builder's run fails on a plan/usage or rate limit, its partial work is committed, no review is spent, the attempt is not consumed, and the PR is labelled `devos:quota-wait`; the same applies when the reviewer hits a Claude limit (review-only resume, nothing recorded in `PHASES.md`). `devos-resume` re-dispatches the oldest parked task hourly while no cycle is running. A builder failure that is not a limit halts without spending a review. | Human question on plan limits (2026-10-10) |
| PR-13 | **No merge before the verdict.** A task PR is merged only after its review: by the runner on PASS, or by the human at a gate. The runner sets the commit status `devos/verdict` (pending → success on PASS, failure on FAIL) and `main` requires it. The runner only ever acts on the branch's **open** PR; if a task's code reached `main` early, the review still runs on the branch and lands as a "review record" PR. Intake runs act only on issues from owners, members and collaborators. | T08: PR #10 merged by hand while the review was pending; Vercel preview step hung with no time limit (2026-10-11) |
| PR-14 | **Main may move during a run.** Before every push the runner merges the latest `main` into the task branch (`scripts/devos/sync-main.sh`), so method patches pushed mid-run never make a task branch look like it edits workflow files. A conflict stops the run with a clear message; re-run the task. Prefer pushing method patches between runs. | T09 a1: push refused ("refusing to allow a GitHub App to create or update workflow") after two method patches landed on main during the build (2026-10-11) |
| PR-15 | **The gate doctor speaks before a merge.** `devos-doctor` keeps one comment per PR saying what stands between it and its merge, and sets the commit status `devos/gate` (green = ready for the human's merge; `devos/verdict` stays the review's own signal). It runs when `ci` finishes on a PR, when the cycle stops at a human gate or halts, and on `/devos doctor`. It re-runs a ci failure that a known rule attributes to the environment once per commit, asks Claude read-only for a second opinion when no rule matches, and offers `/devos revise` for a code cause; it never merges, pushes or edits code. Vercel previews and production deploys are made from a copy without `.git` (with `--meta devosBranch`), so a Hobby team never blocks the runner's commits; screenshots fall back to the local build when a preview answers with the Vercel login. | T10: `ci` build failed on a Google Fonts download after the cycle's checks passed; previews a2/a3 Blocked by Vercel (commit author `devos-runner`); runner screenshots were the Vercel login page (2026-10-11) |
| PR-16 | **A deploy is proven by Vercel's URL, not by a green job.** Every Vercel upload goes through `scripts/devos/vercel-deploy.sh`: it uploads from the project directory (the prebuilt output refers to `node_modules` by path) with only `.git` moved aside, and fails unless Vercel returns a deployment URL. The production smoke test probes that URL with `probe.mjs --strict`; an empty `--base` is an error, never a fallback to a local server. | PR-15's copy-only-`.vercel` upload failed on `1c4813b` ("File does not exist: node_modules/.pnpm/client-only…"), and devos-deploy stayed green: no URL was checked and the smoke test probed a local server (2026-10-11) |
| PR-17 | **The data layer is code, proven every run.** With the backend module active (`supabase/config.toml` exists), every run builds a throwaway local Supabase from the migrations and the synthetic seed, and adds the required checks `db`, `db-test` (pgTAP) and `types`. `guard:data` enforces forward-only migrations, RLS on every table, `search_path` on `security definer`, no write grants to `anon`, the secret key only in `server-only` modules, and synthetic seeds. A schema change always stops at the human gate. No agent touches a hosted project. Method: `docs/method/FULLSTACK_MODULE.md`. | Human request to add a Supabase backend and test the method full stack (2026-10-11) |
| PR-18 | **The database moves before the app, after a backup.** On the human's merge, `devos-deploy` takes a schema dump and an AES-256-encrypted data dump (kept 30 days), runs `supabase db push`, and only then builds and uploads the app. A failure stops the job before the app moves; fixes go forward as new migrations, written expand-then-contract. Previews get no database unless a separate preview project exists (`DEVOS_PREVIEW_DB=true`); without it the review uses the local build against the CI database. | Same request (2026-10-11) |
| PR-19 | **Zones are declared, never assumed.** The `devos:boundary` line in `docs/BOUNDARY_MODEL.md` names the profile and every zone (a staff dashboard, a member area) where forms, cookies and route handlers are allowed; only a signed OD changes it, and `guard:boundary` reads it. Outside a zone the Boundary gate holds in full; analytics and third-party scripts are never allowed by a zone. A zone with personal data brings the Personal-Data Protection gate (handbook §10.3), `docs/PROTECTION_MODEL.md`, and a private repository before it ships. | Same request (2026-10-11) |
| PR-20 | **Heavy runs are announced, and nothing is lost to a limit.** A run is heavy when its review uses the gate model or extra-high effort, or its fence builds at extra-high (`scripts/devos/heavy.mjs`). Before one starts, and when a new phase starts, the runner comments in the "Dev OS: run notices" issue with the reasons and the outlook of heavy tasks ahead. With `DEVOS_HEAVY=hold`, a heavy task's first attempt waits for `/devos go`; retries, resumes and revisions never wait. A planning run (intake) gets 90 minutes, reads the human's answers from the issue thread, plans a "Small change" at high effort, keeps its partial plan on `intake/issue-N` when stopped, and resumes by itself after a usage limit (`/devos intake resume` by hand). Every verdict and plan states what its run cost: minutes, turns, tokens. | Intake #14 took 26 minutes and about half of a Claude usage window; the human asked to be warned before heavy work (2026-10-12) |
| PR-21 | **The review file is the verdict of record.** If the reviewer wrote a complete review file for the attempt (first line `VERDICT: PASS|FAIL`, a ledger, a `Next prompt:` line whose fence exists) but stopped before its structured answer, `verdict.mjs` takes the verdict from the file instead of halting; red checks still override it (PR-08), and a usage limit still parks the run (PR-12). A `review_only` re-run with `reuse_review` keeps such a file and only re-decides. The reviewer's turn limit is 150 and its step 75 minutes; it writes its files first and keeps the next fence's rehearsal proportionate. On the runner's own PRs a `ci` run held for approval is not a blocker. | T12 a1: the reviewer wrote a full PASS and the T13 fence, then ran out of turns (81 of 80) before its summary, and the runner halted (2026-10-12) |
| PR-22 | **The builder works, the reviewer judges.** The builder implements, writes the tests that prove each Done-when (refusals included) and pastes real outputs. The runner runs every check and writes `.devos/evidence.md` (changed files, check results, test counts, guards, report status, and for data work the migrations, `supabase test db`, RLS, policies, grants and a bundle scan). After the build, `scripts/devos/review-mode.mjs` picks the review: **light** (Sonnet, medium effort, 50 turns) for risk 1–2 with nothing critical touched, or **deep** (Opus, high effort, 120 turns) for risk 3, a gate, or a diff touching `reviewer.deep_paths`; a retry raises the effort one step. The reviewer never re-runs the check suite or builds the next task; a fence is a specification, not the code. | T12 a1: one risk-3 review read 14.9M tokens and wrote 99k, re-running every check and rehearsing T13's code; the human asked that heavy work and tests go to the builder and deep review only where it matters (2026-10-12) |
| PR-23 | **One authority for checks on runner PRs.** On `task/*` and `intake/*` PRs, `ci` is skipped: `devos-cycle` already runs the same checks on the same code and folds them into `devos/verdict` (PR-08). If a `ci` run happens there anyway (started by hand), the gate doctor shows its result and diagnosis but does not block the merge. `ci` still runs on pushes to `main` and on human PRs. | T12: a hand-approved `ci` run failed in 2m50s while the cycle's checks on the same code had passed, leaving a red check beside a green verdict and gate (2026-10-12) |
| PR-24 | **A font download is not a failed build.** While the fonts come from Google at build time, a build whose log matches `devos.config.json` `retry_build_on` (the Turbopack next/font/google errors) is retried up to three times, by `run-checks.mjs` and by `devos-deploy`; any other build failure stops at once. The permanent fix is self-hosted fonts (`next/font/local`), to be requested as a small change. | T12: the same font error failed a manual `ci` run and then the production build after the merge, while the cycle's own builds of that code passed (2026-10-12) |
| PR-25 | **Every PR is checked before merge, on GitHub, without approvals.** The cycle posts its checks as the commit status `devos/checks` on the PR's head (pass, or which check failed). If main gained code while an attempt was reviewed, the runner merges main into the branch and re-checks the result before any merge; a red re-check stops the merge. A PR waiting at a human gate is re-checked automatically when main moves (the doctor dispatches a review-only re-decision; no new review). `ci` no longer runs on pull requests (amends PR-23): on a public repository GitHub holds bot-opened runs for approval and they expire as red failures. `ci` checks `main` after every push. Optional: require `devos/checks` in the `main` ruleset next to `devos/verdict`. | T13: two `ci` runs on PR #20 expired unapproved and showed as failures; the human asked for checks that run before every merge automatically (2026-10-12) |
| PR-26 | **Every stack module is declared, emulated and moved by the deploy.** Object storage (R2, `src/lib/r2/`) and Firestore (`firebase.json`) join the database as modules with the same contract: a throwaway local copy every run (S3-compatible store in Docker; Firestore emulator under a demo project id), started for the builder by `scripts/devos/modules.mjs` (also for the task whose fence introduces the module); required checks `storage`, `firestore-seed`, `firestore-rules`; `guard:services` (keys and admin SDKs only in `server-only` files, no Firebase web or tracking SDK, rules never `if true`, rules tests exist, synthetic seed, no service-account file). A Firestore rules change stops at the human gate like a migration. The browser never holds a storage or Firebase key. Production moves only in `devos-deploy`, before the app: a storage preflight (write, public read, delete a probe with the production keys), then Firestore rules, then the seed, which is the source of truth for its collections (removed documents are removed). | Request 3: staff-uploaded images in R2 and a Firestore-backed page added to the reference project to test the method with more backend services (2026-10-13) |
| PR-27 | **What only the human can add is checked by name, asked for once, and waited for without spending attempts.** `devos/setup.json` (method) and `docs/setup-items.json` (product, written by intake) list every secret, variable and Vercel Production variable the project needs, with the steps to add it; `devos-setup` checks names only (never values) on every push to main, every two hours while anything is missing, and on `/devos setup`, and keeps one issue "Dev OS: setup needed" up to date (a comment announces new needs). The cycle does not start without its credentials, the deploy does not start without its settings. A review whose only cause is outside the repository is classified `SETUP`: no fence is reissued and no retry is spent; the verdict names the settings and the steps. Configuration inside the repository stays Grok's to fix. When everything is in place the runner closes the issue, resumes every waiting run and re-runs a production deploy that failed; a cause that cannot be checked by name (a token's permission) waits for the human's `/devos setup`. | The human asked that missing keys and configuration be reported with steps, Grok fix what it can, and the rest wait for him (2026-10-13) |
| PR-28 | **The automation is repaired through the same cycle, never around it.** A "Dev OS method fix" issue is diagnosed by the reviewer from the logs of the runs it links (fetched by the runner) and planned as a Phase `PM` task: risk 3, a `G-Method-<issue>` gate, a fence with `Surface: method` and `Resume after merge`. Method tasks run before any open product task and outside the product order. Grok builds the fix inside `surfaces.builder_method` (method files yes; product, reviewer rules and ledgers no) and proves it with a reproduction; the reviewer reads every changed line. The workflow from main, which the branch cannot change, forces the deep review and the human gate on any change to a method file, and stops a product task that changes one. After the human's merge, devos-advance restarts the task the problem stopped. Workflow-file changes need `DEVOS_PAT` with the Workflows permission. | The human asked that problems in the automated flow be fixed from an issue, with the reviewer planning and Grok implementing (2026-10-13) |
| PR-29 | **A usage limit on one account is not a wait when a second account exists.** Each agent may have two credentials: `CURSOR_API_KEY` / `CURSOR_API_KEY_2` for the builder, `CLAUDE_CODE_OAUTH_TOKEN` (or `ANTHROPIC_API_KEY`) / the `_2` pair for every Claude run (review, planning, revision, doctor). Repository variables `DEVOS_CURSOR_ACCOUNT` and `DEVOS_CLAUDE_ACCOUNT` (1 or 2), or the cycle's run form, choose the account a run starts with; `DEVOS_ACCOUNT_SWITCH=off` keeps it on that one. With switching on, a run that stops on a usage limit continues at once on the other account: the builder from its partial work in the tree, the planner from its partial plan, the reviewer from the start. Only when both are out does the run park (PR-12, PR-20), until the first of them resets. Every switch is noted on the PR. A finished run's own text never triggers a switch (`limit-check.mjs`). | The human asked to switch between two Cursor and two Claude accounts when one runs out, or by his choice (2026-10-13) |
| PR-30 | **The automation has one operating manual, and it cannot fall behind.** `docs/method/AUTOMATION.md` describes the automated cycle as a machine: roles and invariants, every flow, workflow, runner script, guard, prompt, label, status, marker and setting, the failure playbook, and how to change the automation safely. Every method run (intake in method mode, a method fix's build and review, an interactive `/devos-method` session) reads it first. `guard:manual` fails when a workflow, runner script, guard, prompt, repository variable, label or `/devos` command exists that the manual does not name, so every method change updates it in the same PR. Product tasks may not edit it. The "Dev OS method fix" issue takes improvements as well as problems (amends PR-28): the reviewer designs them with the manual's recipes and plans up to three method tasks. | The human asked for the full method in the repository so that later fixes need no outside help (2026-10-13) |
| PR-31 | **A long usage-limit wait never depends on GitHub's schedule, and never floods the issue.** Waits longer than `resume.inline_wait_max_minutes` are handed to `devos-wait`, which sleeps as long as one job may, starts itself again until the reset time, then resumes the parked planning or task; removing `devos:quota-wait` cancels it. `resume.relay` = `public` (default: relay only where runner minutes are free), `always` or `never`; `devos-resume` stays the scheduled backstop. A limit that states no reset time is retried after `default_wait_minutes`, doubling on each repeat up to `max_backoff_minutes`. Automatic planning resumes post no acknowledgement, and the issue keeps one wait comment, updated at each check with the count. | Request 3's planning hit a Claude limit on Oct 13; it was retried hourly 41 times (82 comments), then the stated reset (Oct 16 03:03 UTC) was beyond the inline wait and GitHub's best-effort schedule ran devos-resume only every 3–7 hours, the last time before the reset, so nothing resumed (2026-10-16) |
| PR-32 | **No workflow hands every secret to a step.** Checks that only need to know whether a credential is set receive presence flags (`"1"` or empty), never values; a step that calls a service with a credential receives that one credential. | PR-33 | **No exception for all secrets, and no "latest" lookups on shared runners.** Amends PR-32: `devos-setup` also receives presence flags only; `guard:secrets` fails any workflow with `toJSON(secrets)` and any setup check whose presence list lacks a secret named in `devos/setup.json`. Product secrets (`docs/setup-items.json`) cannot be seen by any workflow, so the setup issue lists them for the human to confirm. Tools are installed at pinned versions: the Supabase CLI at `DEVOS_SUPABASE_CLI_VERSION` (default 2.120.0), because `version: latest` calls GitHub's API, which rate-limits shared runner addresses. | After PR-32, GitHub also held `devos-setup` ("may be malicious"); and `ci` on main after T19's merge failed in 9 s with "Failed to resolve latest Supabase CLI release: rate limit exceeded" (2026-10-16) |
| PR-34 | **Guard deviations are settings.** Catalogues, allowed hosts and route exceptions are `guards` in the generated configuration (PR-40), not constants in the guard files. `guard:data` is unchanged: its rule 4 already accepts the one security-definer function with `set search_path`. | PR-35 | **Motion is evidence the runner captures.** For every page, state and interaction a UI fence names in its `- Screens:` line (default `screens.pages`), `screens.mjs` captures at 1280 and 390 four things: the settled screenshot in normal motion; a filmstrip at `screens.filmstrip_ms`, picked from a CDP screencast, with the real offsets recorded; a reduced-motion screenshot; and the layout-shift value. | PR-36 | **The supervisor acts within limits and speaks once.** `devos-supervisor` may only re-run, re-dispatch, continue from the branch, recover a rescue branch or start the next task, at most `supervisor.max_auto_per_key` times per cause; everything else becomes a proposal the owner approves, an issue, or setup steps. The builder prompt forbids long-lived foreground processes and asks for `timeout` around long commands.
