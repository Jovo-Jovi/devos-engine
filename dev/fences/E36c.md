    - **`adoptPublish`** works through these steps:
      1. It reads the repository's default workflow permissions, and the names of the keys and variables already
         there. It stops when GitHub does not show any of them, so nothing is set over what it cannot see.
      2. It asks for the keys the cycle needs that the repository lacks (hidden when interactive).
      3. It prints what it will do:
         - that Actions may create and approve pull requests, which applies to every workflow of the repository;
         - that the default permissions stay as they are;
         - the labels, the missing variables, and the keys already there, which the cycle will use.

         Then it asks `Type yes to push and open the pull request, or anything else to keep the branch on this
         computer:`. Only a typed `yes` goes on. On a terminal, lines typed while the documents were written are
         dropped first (`read.drain()`). Anything else keeps the branch on the computer and names `devos adopt
         --publish`.
      4. `git push -u origin devos/adopt`, never forced. A rejected push says so and overwrites nothing.
      5. It opens the pull request into `main`, unless this repository's own `devos/adopt` already has one open at
         the pushed commit. A fork's pull request from its own `devos/adopt` is never taken for it
         (`isCrossRepository`, `headRefOid`). The description comes from `adoptPullBody`, written to the staging
         folder. The title comes from `pullTitle`, without `%`, `"` or control characters.
      6. It sets `can_approve_pull_request_reviews=true` and writes the default permissions back unchanged. It
         creates the two form labels, and sets only the variables that are missing (`DEVOS_REPORTING` only after a
         yes to the link). It uploads the typed keys on stdin.
      7. `setup-check.mjs --for cycle`, as `devos init` runs it.

      It never touches the Wiki or the Projects, never dispatches a cycle, and does only what is missing when it
      runs again.

- **Why only one repository setting changes.** Every DEV_OS workflow declares its own `permissions:`. So the
  project's default token permissions can stay as they are; only "Allow GitHub Actions to create and approve pull
  requests" is needed. `devos init` also sets the default to `write` and turns off the Wiki and Projects of a
  repository it creates. For an existing project, neither is done.
- **An independent security read of the publishing code came before issue.** It found four defects, and v1 closes
