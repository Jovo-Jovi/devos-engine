- **What the copies change,** for the report:
  - **`lib/adopt.mjs`:**
    - **What a copy is** (`devosFacts(folder, files)`):
      - a copy tracks both `.github/workflows/devos-cycle.yml` and files under `scripts/devos/`; untracked files never
        count;
      - a project that tracks some of the four markers but not both of those is `partial`. It stops before the brief,

    - **What stops it before the brief** (`adoptStops`, `copyStops`):
      - links the repository tracks where devos writes. For every adoption, the targets now include the lock,
        `devos.config.json`, `devos/answers.json`, the baseline and the copy's kept precedents. A copy's `CLAUDE.md`,
        which is never written, may be a link;

        - an open pull request from a task branch: `task/`, or the copy's own `branch_prefix`;
        - a `devos-cycle.yml` run whose status is not `completed`, asked only when that workflow is tracked;
        - no answer from GitHub;
        - a `devos.config.json` that is a link or not a JSON object (`copyConfig`);
        - a setting that would take away a rule of DEV_OS's (below).
    - **The placement** (`placeEngineFiles(..., { copy: true })`):
      - every engine file the copy has that differs is replaced where it is, its CI too. When the copy has DEV_OS's
        CI at `devos-ci.yml`, the engine's goes there, with or without a `ci.yml`, and the project's `ci.yml` stays;
      - a file of a template's name (its own `.cursor/rules`) is kept;
      - files in DEV_OS's method folders (`scripts/devos/`, `scripts/guards/`, `devos-*.yml` workflows,
        `devos/prompts|roles|ci|schemas|skills/`) that the engine no longer ships are removed (`copyLeftovers`);
      - `docs/method/PRECEDENTS.md` becomes the engine's with the copy's own PR-01 row (`copyPrecedents`). The
        copy's file is kept at `docs/method/before-adopt/PRECEDENTS.md`. Both are written as plain files only.
    - **The settings** (`projectFromConfig`, `ownSettings`): `devos.config.json` becomes the smallest
      `devos/project.json` over `devos/engine.defaults.json`:
      - a different scalar, or a key the defaults lack, is kept;
      - an object is compared key by key;
      - an array keeps the defaults' items and adds the copy's own (`<key>_extra`);
      - `$` comments, `__proto__` and unknown nulls are left out;
      - `surfaces` and the copy's own `_extra` keys are never carried over, and are named when it has them. The role
        surfaces are DEV_OS's;
      - a null, or a change of kind, where the defaults have a value is a problem, and it stops the adoption.
    - **The install** (`installOnBranch`):
      - the copy keeps its key (its config's `project`, when valid);
      - no AI tool writes documents, so only the brief runs;
      - `CLAUDE.md` and the documents stay;
      - `devos.config.json` and `devos/project.json` are on devos's own list of files it writes last;
      - it needs a tracked `docs/PHASES.md`.
    - **The record and the pull request:**
      - `devos/answers.json` `adopted.copy` holds `{ replaced, removed, settings, left }`, each a list of paths;
      - the description names the removed paths and the settings kept, counts the replaced files, and names what is
        left out. All are validated, and in code spans;
      - it says that DEV_OS's rulings bind with the copy's PR-01, that the cycle goes on with the next open task,
        and to merge between tasks.
