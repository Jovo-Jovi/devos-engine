## E40 — A check that hangs fails, it never holds the cycle; the supervisor resumes a run GitHub stopped at its time limit (PR-70, engine 1.4.0)

- Phase: E · Risk: 3 · Gate: you. It is a method change to the check runner and the supervisor, which every
  project runs in its cycle and its CI.
- Builder: grok-4.7 · Effort: medium · Fast: no
- Stages: 1
- Fence version: v1 · 2026-11-01.
- **Why (the owner's request of 2026-11-01: "Make fix to the devos-engine only").** A project's cycle run built its
  last stage, then its checks step printed nothing for 100 minutes. GitHub cancelled the job at its 150-minute
  limit. The review never ran, and no rule woke for a cancelled run, so the task waited with nothing running.
  Two gaps caused it, and both are in the engine today (`main` @ 57582b9):
  - **`payload/files/scripts/devos/run-checks.mjs`** runs every check with `spawnSync` and no time limit. The e2e
    check also first runs `pnpm exec playwright install --with-deps chromium` with `stdio: "ignore"`, so its output
    is thrown away.
  - **`payload/files/scripts/devos/supervisor.mjs`** acts only on runs whose conclusion is `failure`. A run GitHub
    stops at its time limit ends `cancelled`. Its idle rule also skips any task with an open pull request.
- **This task runs before E36c.** Both change `CHANGELOG.md`. E36c's fence is refreshed after this one merges.
- **What the copies change,** for the report:
  - **`payload/files/scripts/devos/run-checks.mjs`:**
    - `limited(cmd, args, { shell, env, minutes })` runs each check with `spawn`, with no input
      (`stdio: ["ignore", …]`):
      - on POSIX the check runs in a process group of its own (`detached`);
      - at its limit it ends with everything it started: SIGTERM to the group, then SIGKILL after 5 seconds, or
        `taskkill /t /f` on Windows;
      - when it ends, what it left running in its group ends too (POSIX). The result comes 2 seconds after its
        `exit` at the latest, even when a process it left behind still held its output;
      - after `exit`, no timer signals its pid, since Windows reuses pids quickly.
    - `run`, `shell` and the module scripts (`pkgScript`) go through it, so every call is now awaited. The
      Supabase CLI checks (`db`, `db-test`, `types`, `db-lint`) take the same limit through `sbLimited`, which passes
      `timeout` to `supabase.mjs`'s `sb` options. Only spawnSync's own timeout counts, never the word in the CLI's
      output. `supabase.mjs` itself does not change.
    - **The limits:**
      - each check has `check_timeout_minutes` (default 30), within `checks_budget_minutes` (default 60) for all of
        them together. A fraction of a minute is allowed;
      - a check stopped at its limit is recorded as `timeout`. Its log ends with the line that names the limit;
      - a check still waiting when the budget is used up is not started. It is also recorded as `timeout`;
      - a required `timeout` fails the checks like any failure.
    - **The browser install** for `e2e` has 10 minutes (or `check_timeout_minutes` when shorter). Its output goes
      to `.devos/logs/e2e-install.log`.
    - **Ctrl-C, SIGTERM or SIGHUP** on the runner start no further check and send SIGTERM to the running ones.
      The runner writes no results (`untilStopped`) and exits 130, 143 or 129 after 3 seconds. Its `exit` hook
      sends SIGKILL to what is left.
    - The limits are clamped to a day, and the script always ends with `process.exit`.
  - **`payload/files/scripts/devos/supervisor.mjs`:**
    - `timeLimit(runId)` reads the run's jobs. A `cycle` job `cancelled` with GitHub's annotation "exceeded the
      maximum execution time" is a run stopped at its time limit. A cancelled `wait-and-resume` never counts:
      cancelling it is how the owner stops a wait. The annotation is read with the workflow's own token
      (`REPORT_TOKEN`), since `DEVOS_PAT` has no Checks access. When it cannot be read, a job that ran its whole
      limit counts: at least the cycle job's `timeout-minutes` minus 1, from `.github/workflows/devos-cycle.yml`.
      `saved` means that the step "Commit and push the builder's work…" succeeded.
    - **Where it is caught.** The event rule and the every-scan rule for the latest cycle run take such a run as
      stopped. A cancelled run wakes no supervisor, so the scheduled scan is where it is found.
    - **The incident.** Its key is `<task>:a<attempt>:time-limit`, its action `redispatch`, and it is review-only
      when the builder's work was saved. A run someone cancelled has no such annotation, and is left alone. The
      existing `max_auto_per_key` limit (2) stops a loop.
    - `classify --run <id>` also prints `review_only`.
    - `history()` reads every page of the supervisor issue (`gh api --paginate --slurp`, the first page with an
      older `gh`). Before, it read only the first 100 comments, so past them the counts per cause stayed 0, and
      `max_auto_per_key` could no longer stop a loop.
  - **`payload/files/dot-github/workflows/devos-supervisor.yml`:** `permissions` gains `checks: read`, for the
    annotation. Nothing else changes in it.
  - **`payload/files/devos/engine.defaults.json`:** `check_timeout_minutes: 30`, `checks_budget_minutes: 60` and
    `check_limits_note`.
  - **The manual and the precedent:**
    - `docs/method/AUTOMATION.md` §4 names both rules in the `run-checks.mjs` and `supervisor.mjs` rows, and §8 names
      the two settings;
    - `docs/method/PRECEDENTS.md` gets PR-70 and "Live maximum: PR-70".
  - **Labels:** `tools/sources.mjs` puts E40 on the 6 payload files.
  - **CHANGELOG** 1.4.0 gets a "Fixes" section with one bullet. The version stays 1.4.0.
  - **Tests:**
    - `test/config-equivalence.test.mjs` leaves out the three new keys, as an engine addition;
    - `test/time-limits.test.mjs` (new), (a)–(d):
      - (a) a hanging check with a child that holds its output is stopped and recorded as `timeout`. Its log names
        the limit, and its child is gone;
      - (b) the budget: the check it stops, and the ones it never starts;
      - (c) `e2e-install.log`, the defaults, the manual and PR-70;
      - (d) the supervisor's `classify` with a stand-in `gh`: a run stopped after the builder's push is re-dispatched
        review-only, one stopped during the build is re-dispatched as it was, and one someone cancelled gives no
        incident.

        It also covers annotations that cannot be read: a `cycle` job that ran its whole 150 minutes is stopped,
        one cancelled after 20 minutes is not, and neither is a `wait-and-resume` cancelled after 200 minutes. It is
        skipped on Windows, where a stand-in `gh.cmd` cannot run without a shell;
      - (e) a check that exits leaving a child that holds its output, and a check that reads its input, both pass at
        once, and the child is gone (POSIX);
      - (f) Ctrl-C during a check: exit 130, no `ci-results.json`, and the check's child gone. It is skipped on
        Windows, which has no SIGINT to send, so Windows has 18 skips.
- **The payload stays generic.** The precedent tells what happened without naming the project
  (`find-specifics` prints `0 0`).
- **An independent security read came before issue.** It found these defects, and v1 closes them:
  - a check that exited and left a child holding its output kept the runner open;
  - a check got an input that never closed;
  - the annotation needs `checks: read`, which neither token had;
  - the counts per cause read only the first 100 comments of the supervisor issue;
  - the Supabase CLI checks had no limit.

  It also made four notes, all taken: Ctrl-C now lets the checks shut down; no pid is signalled after its `exit`
  on Windows; the defaults note no longer claims the review always fits; and the limits are clamped.

  **A second read confirmed those fixes** and found two new defects, now closed with tests (f) and (d):
  - after Ctrl-C, the runner still wrote results and exited 0;
  - with unreadable annotations, a `wait-and-resume` the owner cancelled could count as stopped.

  It also noted that "ETIMEDOUT" in a passing CLI's output was read as a timeout. Now only spawnSync's own
  timeout counts.
