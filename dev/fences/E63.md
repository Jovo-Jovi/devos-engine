### What the package does

### Changes from draft d1, each reported (none weakens a condition)

1. **`work` is a reusable workflow,** not a job of `devos-cycle.yml`. GitHub sends a job every secret its YAML names,
   even behind a false condition, and the builder can read the runner's memory with `sudo`. A called workflow receives
   only what the caller passes, so `work` really holds only the chosen tool's keys. At run time there are still two
   jobs (D2). Engine-side, `.github/actionlint.yaml` lets actionlint skip the one reference it cannot open
   (`./.github/workflows/devos-work.yml` lives under `dot-github/` here); S1 checks the call instead. `engine-ci` is
   unchanged (D8).
2. **`resolve` changes beyond its `needs`:** the builder pick moved there (it reads a label, which `work` may not), and
   the reviewer check. Every job now declares its own permissions; the workflow default is `contents: read`.
3. **The run's commit is `github.sha`,** for both jobs; `resolve` records no SHA. `publish` fetches the branch's head on
   GitHub itself.
4. **The check-only run is `review_only` with `reuse_review`,** two inputs that exist (PR-21): no new input.
5. **T92 item 6** is a link and a `.gitmodules`: the packing step is main's workflow, which the builder cannot change.
   A second ref in the bundle is covered by U3.
6. **One more deployment path** (the table): `setup-issue.mjs` re-runs a deploy that failed for a missing setting.

### Limitations (reported; no condition weakened)

1. **Check results are claims.** `publish` must not run the builder's code, so red blocks and green is believed. The
   required list and its commands come from main; a missing result is red. The review reading the tests, the gates and
   your acceptance (E67) are the controls.
2. **The review can be misled by what it reads** (a planted `CLAUDE.md` in a subfolder, a comment). In `publish` it can
   neither run code nor reach a token, and only its review file and fences are kept.
3. **`work` can send out what it holds:** the builder tool's keys, the media key and the source (D6 (c)). For a
   media task, the builder could also replace the fence's media files or edit `docs/design/media.json`; publish accepts
   those paths because the step before the builder writes them.
4. **The reviewer lost its shell, and the cycle its preview** (D12): every command the reviewer ran is in the evidence;
   screenshots and readiness use the local build, so headers set only in `vercel.json` are not seen by the cycle.
5. **The review user relies on the hosted runner's `sudo`.**
6. **The builder's outcome is a claim held to limits:** a forged one can delay or stop a task (park, halt, up to
   `max_time_slices` slices per attempt, one switch), never pass it.
7. **Until E67,** a PASS from a misled reviewer on a risk-1/2 task still auto-merges into `main` (D1 (a)); production
   waits for your next merge unless a provider deploys from Git.
8. **No ruleset on private repositories with GitHub Free** (D4): there `main` is protected by DEV_OS's code and by who
   has write access.
9. **`devos init` and `devos models` still offer other reviewer tools;** the cycle refuses them with the fix. A
   follow-up can make setup refuse them too.
10. **With Claude Code as the builder, `work` holds the same Claude keys as the review.** A key of the builder's own
    (separate secrets for the builder) is a follow-up; until then the builder could spend or send the review's key.
11. **Your project's own workflows** (`ci.yml`) run on the pushed task branch with what they name, as for any branch
    of yours; keep production secrets out of them. Their files are main's: the branch cannot change one (above).
12. **A method fix that needs a workflow change is applied by you.**
