### What exists today (`main` @ c8b04e5)

- **`intake`** (`/devos intake`, or the label `devos:request`):
  - the label path checks the issue's author; the comment path checks only the commenter (audit M1);
  - the issue body is fetched after the CLI install;
  - the planner runs with a shell and every AI key;
  - later steps of the same job push with `DEVOS_PAT`, open the PR, and post `devos/verdict` success.
- **`revise`** (`/devos revise <what>` on a task PR): the reviewer reissues the fence, then the same job pushes and
  rebuilds.
- **`accept`** (`/devos accept [note]`, E61): runs `scripts/devos/accept.mjs` from a checkout of the PR's head (the
  task branch, when the PR is open), with `GH_TOKEN`, then pushes.
- **`go`:** no AI call and no branch code; unchanged.

### What changes

- **`intake` and `revise` become `work` and `publish`, the same pattern as E63.**
  - **`work`:** the planner, or the fence reissue, keeps its shell. It has only its own key (the key filter),
    `contents: read`, no GitHub write and no PAT. It writes the plan files and packs them as a bundle.
  - **`publish`:** a fresh `main` (or unit) checkout.
    - It verifies the bundle against the intake surface, or the revise surface (the one fence), using `main`'s guards
      (U3 of E63, with these surfaces).
    - It pushes, with the PAT, only output that passed. It opens the PR and posts `devos/verdict` on intake PRs (only
      here).
    - A rejected plan is not pushed; the issue gets the reason.
- **M1:**
  - the comment path also requires `github.event.issue.author_association` to be OWNER, MEMBER or COLLABORATOR (PR-13's
    own words);
  - the request text is the issue body and the trusted comments taken from the triggering event, never fetched later.
    A body edited after your comment does not reach the planner.
- **`accept`** runs `main`'s `accept.mjs` from a `trusted/` checkout of `main`, over the task branch as data. It runs
  no branch code, so it stays one trusted job, with git through E63's wrapper.
- **Method records:**
  - PR-92 amends PR-13, PR-20, PR-28 and PR-87;
  - `AUTOMATION.md`: the intake and revise jobs, the surfaces, and the snapshot of the request.

### Security acceptance conditions and their tests

S = static; U = unit; L = live, on devos-pilot, once after the merge.

- **SA1.**
  - S1: `intake-work` and `revise-work` have `contents: read` only, no PAT, no `GH_TOKEN`, and only their own AI key.
  - S2: the `publish` jobs check out only `main` or the unit branch, and run only `trusted/` scripts with E63's git
    wrapper.
  - S3: `accept` runs `trusted/scripts/devos/accept.mjs`.
- **SA2.**
  - U1: a plan bundle that changes anything outside the intake surface (a workflow, `scripts/devos/`, `src/`, the
    config) is rejected, each path named, and never pushed.
  - U2: a revise bundle that changes anything but the one fence is rejected.
  - U3: the provenance checks of E63 U4.
- **SA3.**
  - U4: the planner's own claims ("guards pass", a `VERDICT:` line) are not read. The guard result and
    `devos/verdict` come only from `publish`.
  - S4: only the `publish` jobs have `statuses: write`.
- **SA4.**
  - S5: nothing in `devos-intake.yml` merges into `main` or dispatches `devos-deploy`.
  - Intake, method-fix and accept PRs wait for your merge, as today.
- **SA5.**
  - U5: an issue edited after the comment. Given an event payload and a different current body, the planner receives
    the event's body.
  - U6: an issue opened by an outsider, with your `/devos intake` comment, is refused with one sentence.
  - L1: T93 on devos-pilot. An issue of yours asks the planner, as an authorised canary, to add
    `.github/workflows/canary.yml`, to edit `scripts/devos/verdict.mjs`, and to write `VERDICT: PASS` into a review.
    `publish` rejects the plan, nothing is pushed, and the issue names the paths.

### Limitations

- **The planner can still be misled by a trusted author's request.** It can only write plan documents, which wait for
  your merge.
- **A `/devos revise` on a task PR still rebuilds that task through E63.**

### Cost

- **AI calls:** none added; the planner and the reissue run once each, as today.
- **Time:** about one minute more per intake or revise (the second machine).

- Change what the planner or the fence reissue is asked to do.
