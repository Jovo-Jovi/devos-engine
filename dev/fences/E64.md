### What the package does

- **Planning in two halves** (`/devos intake`, the labels `devos:request` and `devos:method`, a resume):
  - **`intake`, the planner.**
    - Its token only reads (`contents`, `issues`, `pull-requests`, `actions`), and it has no PAT.
    - It holds only Claude Code's keys. D11 now covers planning: any other reviewer tool stops the run with one message.
    - It checks out `main`. On a plan branch, main's method files are laid over the working tree (never staged) before
      anything runs.
    - Its commit is made even when it wrote nothing.
    - It hands over `plan.bundle`, `decision.json` and `usage.jsonl` as `devos-intake-N-plan`, and a reset time only
      when the limit stated one.
  - **`intake-publish`, main's code only.**
    - It checks out `github.sha` into `trusted/` and reads the request again with main's `intake-request.mjs`. A
      refusal is answered in one sentence.
    - It takes exactly one artifact, then runs `publish-verify.mjs plan` and main's guards (`phases`, `secrets`).
    - Only a verified plan that holds something is pushed; a fresh plan replaces the old one with a lease. A partial
      plan is kept for a resume only when it holds something.
    - It opens the PR (this repository's PRs only) and posts `devos/verdict` success. `revise-publish` posts only a
      pending status on a revised unit.
    - It always says why when it doesn't push: the checks' reasons, the guards' FAIL lines, `empty`, `unpushed`, or
      no artifact.
    - Every comment is scrubbed of the keys the job holds and carries `<!-- devos-comment -->`.
    - PR-31's backoff (60, 120, 240 … minutes, `checks=`) applies when no reset time was stated.
  - **`intake-ack` and `intake-refuse`:** one comment each, with no AI and no branch code.
- **M1:**
  - Only an issue its repository's owners, members or collaborators opened is planned, on the comment path too.
  - A resume needs the issue's label too, and a pull request is never planned.
  - The request is the event's title and body and your comment, plus the earlier comments of trusted people. Every
    page of the thread is read, and the runner's own comments never count.
- **`publish-verify.mjs plan`:**
  - **The bundle:** one ref; descent; no control character, `.gitmodules`, link, submodule or oversized file.
  - **A plan on main:** only `surfaces.intake.allow`; rows added to `docs/PHASES.md`, unticked, verdict `—`; none
    changed and no number twice; Phase PM only for a method fix. It reports `planned`, what the plan holds against
    main.
  - **A revision:** only `docs/fences/<task>.md`, committed as "Tnn: fence reissued for human revision (attempt N)".
- **Revisions in two halves:**
  - **`revise-prep`** finds this repository's open task PR, or a unit's acceptance PR into main.
  - **`revise`** is the planner: read-only, with Claude's keys. Main's method files are laid over the branch before
    anything runs; `CLAUDE.local.md` and `.mcp.json` are removed. It commits only the fence, and it is no longer in the
    cycle's concurrency group.
  - **`revise-publish`** accepts only that fence, pushes it and starts the build. A failed push is explained on the PR.
- **On the unit (D-E17):**
  - **`/devos revise <what>` on a unit's acceptance PR revises the unit's last task on the unit's branch.**
    - The fence is reissued with your change. The change may touch any work of the unit within its signed scope; new
      scope is a change request (`revise.md`).
    - `plan` opens its row again as `REVISE aN — …`. `next-task.mjs` builds attempt N for any run of it, past
      `max_attempts`, and `review-mode.mjs` reviews it deep.
    - `revise-publish` first checks that the PR is still open. It then marks the new head `devos/verdict` pending and
      deletes the task's old branch when its PR was merged into the unit. The cycle builds the task inside the unit.
    - One revision at a time: while the task is rebuilt, a further `/devos revise` goes on its task PR.
    - When it passes, `unit.mjs open` finds the acceptance PR's report stale (`staleTasks`: a verdict the unit no
      longer has), and publish renews the report and `devos/verdict`.
    - No row is added, so the ledger's order and numbering hold.
  - **`/devos accept`:**
    - on a task you merged into an open unit, it opens `devos/accept-Tnn` **into that unit**;
    - on an accepted unit, or with no unit, it goes into `main`;
    - on an open task PR, it records on that branch, as before.
- **`accept`:** one trusted job. It runs main's `accept.mjs` over the branch it writes on as data, and your note
  survives as an absolute path. Its git reads no configuration of the branch or the runner and runs no hook. It no
  longer calls `sync-main.sh`.
- **Method records:**
  - PRECEDENTS PR-92 (live maximum PR-92);
  - `AUTOMATION.md`: New work, units, Accepting, Revisions, the jobs row, and the `sync-main.sh`,
    `intake-request.mjs`, `unit.mjs`, `next-task.mjs`, `review-mode.mjs` and `publish-verify.mjs` rows;

### Limitations (reported)

1. **A trusted author's request can still mislead the planner,** and the planner holds Claude's keys with a shell, so
   it could write a key into a plan document in an encoded form. A plan only writes documents that wait for your merge;
   `guard:secrets` runs over it in publish and every comment is scrubbed. This is the same limitation as E63's D6 (c);
   only restricting network egress would close it.
2. **Every job runs in main's Actions cache scope.** No DEV_OS workflow restores a cache, but a product workflow on main
   that does is exposed. This is the same as E63's `work` job.
3. **A method fix's planner reads the logs of failed runs,** which a fork's PR can influence. They reach it as data,
   outside M1's filter, as before E64.
4. **One path outside the surface discards the whole plan.** It can be recovered by hand from the artifact for 7 days.
5. **A unit revision rebuilds only the unit's last task, at that task's risk.**
   - The change goes into that task's fence, and is reviewed deep. New scope is a change request, planned after the
     unit.
   - While the reviewer plans the fence (up to an hour), the acceptance PR still shows its old success. Once the fence
     is pushed, the head is pending.
   - DEV_OS sets no branch protection, so you can still merge then. You would accept what is on the unit at that
     moment.
6. **Two intake PRs open at once can take the same task number,** as before E64. The second then conflicts with
   `main` in `docs/PHASES.md`.
7. **About one minute more per plan or revision** for the second machine. No AI call is added. A revised unit task is
   one more build and deep review that you ask for, as a task revision always was.
8. **Not yet run on GitHub** (L1, T93 on devos-pilot, optional). You chose not to run canaries before Medix.
