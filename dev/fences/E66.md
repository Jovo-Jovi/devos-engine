### What the package does

- **Every CLI at a pinned version (M3).**
  - `tool_versions` in `devos/engine.defaults.json`: each npm package is its newest release at least two weeks old
    today. A project may set its own in `devos/project.json`.

    | Tool | Pin |
    |---|---|
    | Claude Code | `@anthropic-ai/claude-code@2.1.310` |
    | Codex | `@openai/codex@0.164.0` |
    | Gemini CLI | `@google/gemini-cli@0.65.0` |
    | firebase-tools | `firebase-tools@15.34.1` |
    | Vercel CLI | `vercel@65.2.0` |
    | pnpm | `pnpm@10.34.9` |
    | Cursor's agent | `2026.11.05-86047df`, SHA-256 `170b7778…535442e` of its linux/x64 package |

  - `scripts/devos/pins.mjs <tool>` prints the npm spec, or Cursor's version and hash. It reads the
    `devos.config.json` at the root its own `scripts/` folder is in, so a trusted job's copy (`$T`) reads main's. It
    fails on `latest`, a range, or a missing pin. Every install takes it as `spec=$(…)`, so a failure stops the step.
  - **The work job reads every pin from main,** before the task branch is checked out. firebase-tools, installed after
    that, takes the pin read then (a step output).
  - **Where:**
    - the work job (pnpm, the builder's CLI, firebase-tools);
    - `ci.yml` and `devos-deploy.yml` (pnpm, firebase-tools; the deploy's Vercel CLI);
    - the planner (intake and revise), the supervisor, and the review's own user (`review-user.sh`);
    - `vercel-deploy.sh`.
  - **Cursor:** its agent package is downloaded by version from `downloads.cursor.com`. Its SHA-256 is checked before
    it is unpacked, and it is linked as `agent` and `cursor-agent` in `~/.local/bin`, as Cursor's installer does.
    This replaces `curl https://cursor.com/install | bash`.
  - **Actions:** the three third-party actions are pinned by commit, at the version their tag gave on 2026-11-09:
    - `astral-sh/setup-uv` (v6.8.0);
    - `subosito/flutter-action` (v2.23.0);
    - `supabase/setup-cli` (v1.7.3).

    GitHub's own actions stay on their major tags (the final plan). The toolchains those actions set up (uv, Go,
    Flutter) follow their stable release, and the Supabase CLI keeps its PR-33 pin.
- **No agent's raw output in an artifact (D9).**
  - The doctor's and the supervisor's artifacts leave out `claude.json` and `claude.err`.
  - Publish's evidence leaves out `reviewer.json*` and every `*.stream.jsonl`.
  - The work job's pack already left out the builder's streams and logs (E63); it now also leaves out
    `builder-last-action` and `builder-timeline.json`, the builder's last action and its plan and notes.
  - The journal, the check logs and the evidence are kept.
- **New projects protect main (D4, M4).** `devos init`, after the first push:
  - gives the workflow token read only (`default_workflow_permissions=read`; every DEV_OS workflow names its own
    permissions), and still lets Actions open and approve pull requests;
  - creates the ruleset `devos-main` on `main`:
    - a pull request for every change, with no approval required;
    - no force-push or deletion;
    - `devos/verdict` required;
    - repository admins bypass it.

    An existing `devos-main` is kept. A refusal (a private repository on GitHub Free) is said in one line, and setup
    goes on.

### Changes from the final plan, each reported (none weakens a condition)

1. **`default_workflow_permissions=read` for new projects:** this is the audit's Fit for M4. The final plan's line
   names only the ruleset.
2. **The ruleset is `devos init`'s only.** `devos adopt` leaves an existing project's repository settings as they are:
   its own automation may push to `main`.
3. **Cursor is pinned too:** this is the Fit's spike. Cursor publishes no hash, so the pin is the hash of what its
   installer served on 2026-11-09.
4. **No Dependabot:** the Fit proposed one; the final plan did not. The pins move with each engine release.
5. **Publish's evidence also leaves out `reviewer.json*` and `*.stream.jsonl`,** not only `reviewer.json`. The work
   job's pack also leaves out the builder's last action and timeline.
6. **Codex's effort argument loses its quotes** (`lib/init.mjs`), so L4 does not stop `devos init` with Codex on
   Windows.

### Limitations (reported)

1. **Cursor's pin is trust on first use.** The hash is of the package Cursor's installer served on 2026-11-09. That
   version is four days old, not two weeks, as the installer offers no older one. Only linux/x64 is pinned (GitHub's
   runners).
2. **Pins age.** A newer CLI arrives with an engine release (`devos upgrade`) or your own `tool_versions` in
   `devos/project.json`. Cursor's needs both `version` and `sha256_linux_x64`. A vendor may retire an old CLI; the
   cycle then fails at its install or first call, and a newer pin fixes it.
3. **Your own pull requests into `main`** (`devos upgrade`, `devos models`, a hand-made one) carry no
   `devos/verdict`. You merge them as an admin with "bypass rules". The cycle's acceptance, method-fix and intake
   pull requests carry it. With D4 (a), your PAT bypasses too.
4. **The ruleset is created once, at `devos init`.** Projects set up earlier, and adopted ones, have none, and
   `devos doctor` does not report it. On a private repository, rulesets need GitHub Pro, Team or Enterprise Cloud.
5. **A new project's own workflows without a `permissions:` block get a read-only token.** That is the point of
   M4, but a workflow you add later must name what it needs.
6. **`winQuote` also refuses a tool's own path with `%`** (a Windows user folder named so). The run stops with its
   message.
7. **The toolchains are not pinned:** `astral-sh/setup-uv` installs the newest uv, and Go and Flutter follow `stable`.
   The Supabase CLI is pinned by `DEVOS_SUPABASE_CLI_VERSION` (PR-33), not by `tool_versions`.
8. **Not yet run on GitHub:** the ruleset call, Cursor's download and the pinned installs (no live test until every
   task is done).
