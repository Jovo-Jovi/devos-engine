## E67 — Branch-based development and your acceptance (PR-91, engine 1.14.0) — PROPOSAL

- Phase: E · Risk: 3 · Gate: you. A method change: where task PRs merge, an acceptance PR per unit of work, what starts
  the next unit, the doctor's deployment checks, the precedents, the manual and `dev/PLAN.md` §12.
- Builder: grok-4.7 · Effort: low · Fast: yes (an exact-file package)
- Depends on E63 (`publish`, the trusted path). Comes before E64, so that intake plans land on the open unit.
- Fence version: **proposal d1 · 2026-11-09 · for the owner's approval; nothing is built before it.**
- **The owner's word, 2026-11-09, 11:02:**
  - DEV_OS develops features, modules and phases on their own branches. At a unit's end it runs the checks and the
    review, writes a completion report, gives a preview URL when the provider supports one, and stops at your explicit
    acceptance.
  - You can test, inspect, ask for revisions, or verify another way. It merges into the target branch only on your
    approval.
  - Tests, an AI PASS, a finished task or a preview are never an authorization to merge.
  - Previews get no production secrets by default; preview credentials are isolated and scoped; branch code gets no
    publishing credential; a production deploy is a separate authorized operation.
  - The two jobs, the nine decisions and the no-added-AI-cost rule stay.

### What exists today (inspected on `main` @ c8b04e5)

- **Branches and PRs.** Each task is built on `task/Tnn`, from `main`. Its PR is opened with `--base main` (the cycle's
  "Open the pull request" and "Commit and push the review"). `devos.config.json` has a `base_branch`, which `loop.mjs`,
  `evidence.mjs`, `verdict.mjs` and `review-mode.mjs` read, but the workflows hard-code `main`.
- **Merge gates.** "Act on the verdict":
  - `merge` labels the PR `devos:auto-merged`, runs `gh pr merge --merge --delete-branch` (with the PAT when it is set),
    and dispatches the next task;
  - `human_gate` labels the PR and waits for your merge. That applies to a row with a Gate or with risk 3
    (`isHumanGate`, `lib.mjs`), and to `human_gate_paths` (PR-72).
- **Advance.** `devos-advance` starts the next task when a person merges a PR from `task/`, `intake/` or
  `devos/accept-`. It skips runner merges.
- **Deploy.** `devos-deploy` runs on a push to `main` (it skips `devos:auto-merged`) and on a dispatch:
  - the Supabase backup and migrations, Firebase rules and seed, R2, and Vercel production.

  Vercel's own Git deployments and Supabase's GitHub integration, when a project has them on, deploy outside it.
- **Previews.**
  - The cycle makes a Vercel preview per attempt, from the Preview environment.
  - Setup puts the module values (Supabase, R2, Firebase) in Vercel's **Production** environment only (setup items
    `supabase-vercel`, `r2-vercel`, `firebase-vercel`).
  - A preview database is opt-in (`DEVOS_PREVIEW_DB`, PR-18).
- **PHASES.md.** `Task | Phase | Station | Name | Risk | Gate | Done | Verdict`. The method's gates already mark the
  feature and module boundaries: G-Foundation, G-Public, G-Dashboard, G-Feature, G-Harden and G-Launch (handbook §3).
- **So today:** auto-merged tasks land on `main`, production moves at your next merge, and `main` itself is not gated.

### Proposal — the smallest coherent change

1. **The unit of acceptance.** `devos.config.json` gains `acceptance.unit`:
   - `gate` (proposed default): a unit ends at every row with a Gate, and at the last row of each phase;
   - `phase`;
   - `task`: every task waits for you, at no AI cost.

   You can end a unit anywhere by putting a Gate on that row of `docs/PHASES.md`, so feature, module and phase
   boundaries all use the column the method already has.
2. **The unit branch.**
   - `resolve`, which is trusted, creates `devos/unit-<last task>` from `main` when a unit starts.
   - Task PRs target it.
   - Sync, evidence and verdict use it as their base, through the existing `base_branch` reads and a `DEVOS_BASE`
     that `resolve` sets.
3. **Inside a unit, D1 (a) holds.**
   - A risk-1/2 PASS auto-merges into the unit branch (`publish`, with `github.token`).
   - Risk 3 and `human_gate_paths` still wait for you on their own task PR.
4. **At the unit's last row,** `publish` opens the acceptance PR (unit → `main`) and the cycle stops. The PR carries:
   - **a completion report,** made from the unit's own files with no AI call: each task with its verdict file, the
     checks, risk and gates, the changed paths, and open follow-ups;
   - **how to verify:**
     - a Vercel preview of the unit's head (Preview environment), when `DEVOS_VERCEL` is on;
     - otherwise the commands to test locally (`git fetch origin devos/unit-T07 && git switch devos/unit-T07`, and the
       stack's dev command);
     - or "your provider's preview of this branch";
   - **`devos/verdict` success** on the unit's head, from `publish`, for the D4 ruleset;
   - **the label `devos:acceptance`.**
5. **What you can do on the acceptance PR:**
   - **Merge it.** GitHub's merge button is the only way into `main`; the runner never merges a PR whose base is the
     target branch.
   - **Comment `/devos revise <what to change>`.** E64's planner adds a revision task before the unit's last row, on
     the unit branch, and the cycle builds it. This is your request through the existing planner, not an added review.
   - **Close it.** The unit stays on its branch.
6. **After your merge,** `devos-deploy` deploys (it is your merge), and `devos-advance` starts the next unit.
7. **Readers of the open unit branch:** `devos-advance`, `/devos accept` (E61), intake (E64) and `devos-state` read
   PHASES and the fences from the open unit branch, and `/devos accept`'s PR targets it.
8. **The doctor's deployment checks.** It warns when:
   - the Vercel project deploys from Git on `main` (Vercel's API, the project's Git link);
   - a Vercel variable targets both Production and Preview;
   - with the backend module, `DEVOS_PREVIEW_DB` is off but previews are on.
9. **Method records:**
   - PR-91;
   - `AUTOMATION.md`: the setting, the branch prefix, the label, the acceptance PR, and what `/devos revise` does
     there;
   - `dev/PLAN.md` §12;
   - D-E17 in `dev/DECISIONS.md`.

### The security requirements, and where each holds

- **No production secrets in previews by default.**
  - Setup keeps the module values in Production only (today).
  - The doctor warns about a variable shared by Production and Preview.
  - A preview database stays opt-in.
- **Preview credentials isolated and scoped.**
  - The Vercel token exists only in `publish` (E63).
  - Previews are built by Vercel with the Preview environment.
  - The protection-bypass secret reaches deployments by Vercel's design (a limitation).
- **Branch code gets no publishing credential.** That is E63.
- **Production deploy is a separate authorized operation.**
  - `devos-deploy` runs on your merge into `main`, and nothing dispatches it (E63 S7).
  - Provider Git deployments are flagged by the doctor.
- **The two jobs, the decisions, and no added AI cost are kept.** The report is deterministic, and revisions are your
  own requests.

### Conflicts with the accepted decisions (reported, not resolved silently)

- **D1 (a), auto-merge.** It stays, but lands on the unit branch; `main` takes only your merge, as the new requirement
  says. That is the reading taken. If you meant no auto-merge even into a unit, `acceptance.unit: task` gives it, at no
  token cost.
- **D4, the ruleset with `devos/verdict` required.** Acceptance PRs get the status from `publish`; your other PRs use
  the admin bypass. On a private repository with GitHub Free there is no ruleset: "never merged without you" then rests
  on DEV_OS's code and on who has write access.
- **PR-72, `isHumanGate`.** Under `gate`, a row with a Gate no longer waits on its own task PR: the unit's acceptance
  is your signature, once per unit. Risk 3 and `human_gate_paths` still wait per task (Q2 below).
- **E61, `/devos accept`.** Its PR targets the unit branch.
- **Projects already running.** `devos upgrade` starts units at the next task; nothing on `main` is rewritten.
