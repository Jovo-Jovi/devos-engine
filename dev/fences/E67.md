### What the package does

- **Units.** `devos.config.json` gains `acceptance.unit` (`gate` default, `phase`, `task`). A unit is a run of product
  rows ending at a row with a Gate or a phase's last row (`gate`). Its branch is `devos/unit-<its last task>`. Method
  fixes (Phase PM) are in no unit: they target `main` and wait for you, as before (PR-28).
- **`resolve`** (main's code) finds the open unit through GitHub (`unit.mjs open`: the `devos/unit-*` branches whose
  rows are not all ticked on main; a unit's tasks come from its own `docs/PHASES.md`), lays its fences over main's,
  runs `next-task.mjs --unit-phases` (product progress from the unit, method rows from main), and `unit.mjs place`
  says where the task is built (`base`: main or the unit's branch, `base_sha`, `unit_new`), or that the run opens the
  unit's acceptance PR (`accept`), or waits for you (`waiting`: its acceptance PR is open, or you closed it). Two open
  units stop the run.
- **`work`** starts the task branch from the base's commit and merges it (`devos-work.yml` input `base`).
- **`publish`** verifies against the base (`publish-verify.mjs verify --base`, `sync` merges the base), makes a new
  unit's branch from main at the run's commit (`gh api git/refs`), opens the task PR into the unit, and merges a PASS
  into it, never into main: before `gh pr merge` it reads the PR's base, and a base that is not this run's unit
  (`main`, or another unit) turns the merge into a human gate. A product PASS waits on its own PR only at risk 3 or for
  `human_gate_paths`/a schema change (`waitsOnTaskPr`, `verdict.mjs`); a Gate is signed by the unit's acceptance.
- **Acceptance** (a run with no work job, `publish` step "Open the acceptance pull request (PR-91)"): one PR
  `devos/unit-Tnn` → `main`, labelled `devos:acceptance`, its body `unit.mjs report` (each task's verdict, review file
  and PR, the paths it changes, the commands to run it locally, how to see Vercel's own branch preview), `devos/verdict`
  success on the unit's head, the doctor dispatched, and nothing else built until you merge or reopen it. No AI call.
- **Your merge** of it deploys (`devos-deploy`, unchanged triggers) and `devos-advance` starts the next unit. A task PR
  you merge into a unit (risk 3) reads that unit's progress in `devos-advance` (PR-87 kept).
- **The doctor,** on an acceptance PR: Vercel's own preview of the branch, and two warnings, names only: Vercel deploys
  `main` from Git (no `git.deploymentEnabled.main: false`, no Ignored Build Step), and a variable Production and
  Preview share.
- **The supervisor** counts an open acceptance PR as waiting for you (no idle dispatches).
- **The reviewer's prompt** says where a PASS merges.
- **Method records:** PRECEDENTS PR-91 (live maximum PR-91), `AUTOMATION.md` (§1 invariant, §2 units, §3, §4,
  §7 label and branch, §8 setting), CHANGELOG `1.13.0 — Unreleased` (two bullets), `dev/DECISIONS.md` D-E17,
  `tools/sources.mjs` (`unit.mjs`), `payload/manifest.json`.

### Security: what holds, and the tests

`test/units.test.mjs` (S = the workflow files, U = the scripts on crafted inputs); the 21 tests of `two-jobs.test.mjs`
still pass unchanged.
- **Only your merge reaches main.** S1: the payload's one `gh pr merge` is publish's, after the base check (a PR whose
  base is `main` or another unit waits for you); no script merges (the local `devos loop` on your machine excepted).
  S2: the acceptance PR is opened only by publish's step, from the unit's branch into `main`, and never merged by it;
  with no work job, every build step of publish is skipped.
- **The unit and the base come from main's code and the runner's files.** `unit.mjs` and `next-task.mjs` run from
  main's checkout; a unit's PHASES and fences are written only by the runner and the reviewer (the builder's changes to
  them are rejected by `publish-verify.mjs`, PR-90); only this repository's PR is a unit's acceptance PR. U1
  boundaries; U2 open units and the place for each case; U3 the progress overlay; U6 verify and sync against a unit
  branch, and a base that is neither `main` nor a unit refused; U7 `open` and `place` through a stand-in `gh` (a fork's
  PR and a stale closed PR ignored, an orphaned unit stops). S4: `devos-advance`, the supervisor and the local loop.
- **`resolve` writes only through GitHub's merge API,** main into the open unit (S5): never `main` as the base, no git
  of its own, main's scripts and GitHub's actions pinned by commit only.
- **Production stays a separate operation.** S3: `devos-deploy`'s triggers are unchanged; your merge of the acceptance
  PR deploys; nothing dispatches it (E63 S7). U5: the doctor's deployment warnings, names only, never a value.
- **The two jobs, D11, D12 and no added AI cost** are kept: no new agent call; the report is deterministic.

### Limitations (reported)

1. **Progress reaches `main` at acceptance:** `devos status`, `devos-state`'s history and the Tower see a unit's tasks
   once you merge it.
2. **Until E64,** `/devos revise` and `/devos accept` target `main`; an accept on a task inside a unit ticks main's row
   only.
3. **An intake plan merged into `main` while a unit is open** runs after that unit.
4. **Closing an acceptance PR stops product work** until you reopen it; the supervisor may then report the cycle idle
   after its retries.
5. **No ruleset on a private repository with GitHub Free** (D4): "only your merge" rests on DEV_OS's code and on who
   has write access to `main`.
6. **The two-job cycle and the units have not run on GitHub yet.** One short task on devos-pilot after the merge
   (L, optional, about 20 minutes) shows a GitHub-only failure there instead of in Medix.
