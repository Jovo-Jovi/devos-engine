### What the package does

- **N1, the supervisor proposes and you approve.**
  - **Your PAT.** `DEVOS_PAT` leaves the job's level. It is `OWNER_TOKEN` in the two steps that act ("Approve or reject a
    proposal", "Act and report"). Reads and reports use the built-in token.
  - **Where `OWNER_TOKEN` is used.** Only these: a dispatch, a re-run, a rule's continuation, an approved issue or
    comment, and a rescue.
  - **The diagnosis.** Claude Code runs as `devos-review` through `review-user.sh` (setup, workspace, run, stop):
    - in a copy of main's checkout and the facts, with links removed;
    - with `--setting-sources user --settings /opt/devos-tools/settings.json --strict-mcp-config`;
    - with only Read, Glob and Grep.

    Its output is scrubbed of the four credential names before any line of it is printed or read.
  - **What it writes is data.** Each field is plain text, bounded, with `<` and `>` escaped, so it can hold no marker. An
    action outside the schema's list is escalated.
  - **What waits for your approval.** These Claude Code choices are only proposed:
    - `method-issue` and `request-issue`;
    - `revise-with-note`;
    - `revise-continue`, with fixed words.

    The report shows the exact title, body or comment in a fence. `/devos approve <id>` does it with your token.
  - **The history.** Only comments by `supervisor.bot_login` (default `github-actions[bot]`) count, and only each one's
    last marker. A marker carries `<` and `>` as JSON escapes. An id must be `[A-Za-z0-9-]{1,80}`.
  - **A task's pull request.** A "### Dev OS" or `/devos revise` comment counts only from a bot, or from an owner,
    member or collaborator.
- **N2, steps 1–3: publish checks the guards and the secrets before any push.**
  - **The step.** A new step, "Main's guards, before any push" (`publish-verify.mjs guards`), runs after the bundle is
    verified. It runs main's `run-all.mjs --json` on the verified tree with:
    - no secret, token or package manager;
    - `DEVOS_GUARDS_NO_AUDIT=1`, so `guard:deps` leaves its audit to the work job;
    - the run's base as `DEVOS_SCOPE_BASE`;
    - a cap of 300 s.

    It also runs main's secret rules on every file this run changed, read from the head that would be pushed.
  - **What it rejects.** A secret, guards that do not finish, or rules that cannot load. Then `verify.json` has
    `ok=false`, "Rejected by publish" posts the reasons, and nothing is pushed.
  - **What it does not reject.** Any other guard result goes to `guards.json`. `checks` then makes publish's run the
    `guards` result, `reported_by: "publish"`, red too when the work job's was.
  - **The secret's text.** `guard:secrets` names the file, the line and the rule, never the line's text: the work job's
    public log no longer repeats a secret.
- **N6, the builder's details.**
  - `verify --trusted-models` keeps the work job's model only when it is one of these, or one of its effort and Fast
    variants:
    - a model, family or fallback id in main's `agents` and `builder`;
    - this run's choice: `pick_model`, `builder_model`, `builder_fallbacks` and `vars.DEVOS_BUILDER_MODEL`.

    Otherwise it is `unknown`.
  - Effort and Fast come from their fixed lists.
  - The reviewer's prompt and the builder's commit take `steps.vb.outputs.builder_model`, `builder_effort` and
    `builder_fast`, never `needs.work.outputs.*`.
- **I1:** no payload workflow has `${{ … }}` inside a `run:` script. Inputs and step outputs reach scripts through
  `env:` in `devos-cycle.yml` (resolve), `devos-advance.yml`, `devos-deploy.yml` and `devos-doctor.yml`.
- **N3:** `setup-go` with `cache: false` and `setup-uv` with `enable-cache: false`, in `ci.yml` and `devos-work.yml`.
- **N4:** every `actions/*` is pinned by commit in every payload workflow:
  - `checkout` `de0fac2e…` (v6.0.2);

  Each is the commit its tag gave on 2026-11-10.
- **C1, an issued fence changes only upward.**

  - Every fence taken is written to `.devos/fence-changes.txt` (`new, Fence version n` or `Fence version a → b`), which

  - A unit's acceptance report lists the fences the unit adds or changes.

### Limitations (reported)

1. **Tests, lint, typecheck and build are still the work job's claim before the push** (N2 steps 4–5). Running them in
   a trusted job means a third job, which your decisions exclude. A red still blocks, and a secret no longer reaches
   the push.
2. **The dependency audit stays the work job's:** publish runs no package manager on a branch's files.
3. **Secret rules are patterns.** A key in a form they do not know (a Cursor key, for one) is not found.
4. **The guards in publish read the branch's files.** A file built to slow them meets the 300 s cap, and the bundle is
   then rejected (fail closed).
5. **A reviewer can still change a fence openly,** by raising its version. The verdict comment and the acceptance report
   show it, for you to read.
6. **A Claude Code choice of `redispatch` or `rerun-failed` stays automatic:** it carries no text, and
   `max_auto_per_key` bounds it.
7. **A builder model id outside the configured ids and their effort and Fast variants** shows as `unknown` in the
   commit and the prompt.
8. **Any bot's comment on a task's pull request counts** (an app installed on the repository).
9. **Not yet run on GitHub:** see "For the owner, after the merge".
