### What went wrong

- The Tower's `ci` run on the adoption's merge (`e505848`) passed. Its `devos-deploy` run failed at "Settings the deploy
  needs (PR-27)": `MISSING supabase-vercel` and `MISSING production-url`.
- `devos-setup`, on the same commit and with the same Vercel project, found `supabase-vercel` in place and only
  `production-url` missing. The two checks disagree because only one of them could ask Vercel.
- **The cause.** `setup-check.mjs` lists the Vercel project's Production variable names through Vercel's API with
  `VERCEL_TOKEN` and `VERCEL_PROJECT_ID` (and `VERCEL_ORG_ID` for a team) from its environment. Until 1.13.1 the deploy
  job's level held them. E69 (PR-95) moved them into the Deploy step only, so the settings check received presence flags
  (`"1"`) alone. It then cannot ask Vercel, notes "Vercel access is not set up", and reports every item of kind `vercel`
  missing.
- **Who it hits.** Every project with `DEVOS_VERCEL=true` at 1.13.2: each production deploy stops at the settings check.
  The deploy before it stays live. mawsim is still on 1.13.1, so it is not hit.
- E69's test (i) missed it: it skipped every step that carries `SECRETS_JSON`, so it never looked at the settings check.

### What the package does

- **The step.** "Settings the deploy needs (PR-27)" gets `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` from
  the repository's secrets, beside its presence flags, exactly as `devos-setup`'s check step has them. A comment says why
  (PR-96). It runs only `setup-check.mjs`, after pnpm and before the project's dependencies and the deploy's CLIs are
  installed. The job's level still holds no secret; the CLIs step and the guards hold none.
- **The job's comment** now says the Vercel token is in the settings check and the Deploy step only.
- **Records:**
