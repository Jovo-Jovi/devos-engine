## E85 — Review and planning in their own jobs, on any of the four tools; one output contract for every agent run

(The owner, 2026-11-25: "I want to be able to use any AI model as a Builder or Reviewer in projects generated by
DEV_OS, and easily switch between models … The Reviewer can run at the same trust level as the Builder, provided it runs
in a separate job/environment and never has access to write tokens, publishing secrets, merge permissions, or other
privileged credentials. … The Reviewer may run shell commands and tests … Drop E84." On v1 he asked for four more
points: isolation guaranteed, an optional `provider` apart from tool and model, a contract that does not assume a CLI,
and verification that the four tools keep their behaviour while a real run validates the job.)

### The change

**1. The cycle runs `resolve` → `work` → `review` → `publish`.**
- **`review` is a new job** (`devos-review.yml`), called like `devos-work.yml` and placed between them:
  - **Inside it, with main's code:** the bundle is verified (`publish-verify.mjs verify`, `guards`, `state`,
    `checks`), the review is planned (`review-mode.mjs`) and the review tree is built (`review-tree`).
  - **Then the reviewer:** its CLI is installed at its pin (`install-agent.sh`, run from main's checkout), and the
    project's reviewer agent runs with its shell through **`plan-agent.sh reviewer`**. That is the runner the planner
    already used for all four tools: accounts, next models, server retries, and the tool's reviewer kit.
  - **No agent runs** when the bundle is rejected, the builder did not finish, or the review is kept (PR-21, PR-25).
- **`publish`** keeps every step before *Review plan* and after *Take the review's outputs*. Its in-job review goes:
  - out: `review-user.sh setup`/`workspace`/`run`, the Claude-only *Reviewer* step, *End the review user's processes*;
  - in: it downloads `devos-Tnn-aN-review` into `review-out/`, a step checks it, and `take-review --from
    "$GITHUB_WORKSPACE/review-out"` runs as before.
- **`resolve`** loses the Claude-only check. It outputs `review_tool` and `light_tool` instead, and the caller hands
  the review job only those tools' keys.
- **When the review job ends with no review of the verified head,** publish pushes the builder's work and stops with
  `the review job ended … the review runs again (review only)`. The supervisor's new rule then redispatches it review
  only (`T…:a…:review-job`), as a stopped reviewer step was before.

**2. The security boundary. Each item is a test (two-jobs S6, S6b, S6c):**
- **The review job's privileges:**
  - `permissions: contents: read`, at the workflow and at the job level; no `id-token`, no `: write`;
  - no `DEVOS_PAT`, `OWNER_TOKEN`, Vercel, Supabase or Firebase secret, and no `secrets[…]` or `toJSON(secrets)`;
  - only the secrets the caller passes: `KEY_1/2`, `ALT_1/2` (the deep reviewer's tool) and `LKEY_1/2`, `LALT_1/2`
    (the light reviewer's, when it is another);
  - its checkouts keep no credential, and it calls no `gh` and no `git push`.
- **What crosses to publish:** separate runners, so no shared workspace. The only channel is one artifact holding the
  review file and fences, `reviewer.json`, `reviewer-run.env`, `accounts.md`, the usage records and the reviewed head.
  It is scrubbed of the job's keys before upload and never holds the agent's raw output (D9).
- **Publish runs nothing from it:**
  - it checks the reviewed head equals its own verify's;
  - it keeps from `reviewer-run.env` only lines of `code|used|tool|model=<plain>` and `accounts="<digits>"`, and from
    `accounts.md` only `- reviewer: …` lines;
  - its usage records pass `publish-verify.mjs usage`;
  - `take-review` takes only the review file and fences, and `scrub.mjs` removes every reviewer tool's keys.
- **The rule over every workflow DEV_OS installs:** a job holding a write token, the PAT or a publishing secret runs
  no AI call (`claude|agent|gemini -p`, `codex exec`, `plan-agent.sh`, `run-agent.sh`, `agent-watchdog.sh`). The AI
  jobs are exactly: `work`, `review`, the planners `intake` and `revise`, and the two **deferred** second opinions,
  the supervisor's and the doctor's, which run as `devos-review` with no shell (`review-user.sh`, unchanged).
- **The planner jobs** already hold a token that only reads. They lose *The planner is Claude Code*. They install the
  reviewer's tool, and each run gets only its tool's keys. **One limit, stated:** the job itself names the four AI
  tools' keys (never the PAT or a publishing secret), because a job's key mapping cannot depend on a step's output.
  E86 hands it only the planner tool's keys, through a called workflow.

**3. The agent output contract** (`scripts/devos/agent-result.mjs`, contract 1). Every run of the builder (in the work
job, `.devos/builder-result.json`), the reviewer and the planner leaves one object, beside the tool's own output:
- **`agent`:** the execution interface (cursor, claude, codex, gemini, or any id). `tool` is the same value, kept for
  every reader before the contract.
- **`provider`:** the AI service, `agents.*.provider` when set, else `null`. It is optional on any agent in
  `devos/project.json`: an id of letters, digits, `-` and `_`. Projects without it validate and run as before.
- **`model`:** the id, passed to the agent as it is.
- **The run itself:** `exit_code`, `is_error`, `subtype`, `result` (the final text, at most 8000 characters), `usage`
  (input, output, cache read and cache write tokens), `structured_output`, `permission_denials`, `limited`,
  `not_before`, and `duration_ms` and `num_turns` when the tool gives them.

The four tools' outputs are read by the parsers that read them before (`usage.mjs`, `limits.mjs`, `agent-cli.mjs`).
**Any other agent needs no parser:** an object of the contract's own shape is read as it is, and anything else as plain
text. That is the hook E87 uses for API agents, multi-provider CLIs and custom integrations. Nothing in the contract
or the job assumes a CLI: the job runs a runner, and the runner leaves the object. `verdict.mjs` reads `limited` and
`not_before` from it, and the run's own words as before. The review file stays the verdict of record (PR-21).

**4. What changes for an existing project:**
- No change to `devos/project.json`, and no upgrade question.
- A Claude Code reviewer now has its shell and the planner's flags, plus the documentation lookups it had in publish
  (`--mcp-config devos/ci/mcp.claude.json`, `mcp__context7` and the three `WebFetch` domains).
- Cursor, Codex and Gemini reviewers and planners now run.
- The reviewer prompt says it may run the one command that settles a question.
- `tools/review-probe.mjs` and its tests are removed. E84 stays dropped; its files remain on main as a record.
