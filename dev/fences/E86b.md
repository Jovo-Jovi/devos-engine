### The change

1. **Keys chosen by name, in the caller.**
   - `tools.mjs secrets --tool T --as ROLE` (new) prints the names of the secrets the tool reads, from its registry
     file: `ROLE_key=` and `ROLE_alt=` (empty for an empty tool, and an unknown tool stops with `no tool`).
   - `resolve` (`devos-cycle.yml`) writes them for the builder, the deep and the light reviewer: `builder_key`,
     `builder_alt`, `review_key`, `review_alt`, `light_key` and `light_alt`.
   - The work and review calls pass each secret only when its name is the one `resolve` gave, named literally:
     `(needs.resolve.outputs.builder_key == 'CURSOR_API_KEY' && secrets.CURSOR_API_KEY)`. Never `secrets[…]`, which
     sends the job every secret.
2. **Generic inside.** The AI jobs hold the keys only as `DEVOS_KEY_1`, `DEVOS_KEY_2`, `DEVOS_ALT_1` and `DEVOS_ALT_2`.
   - `accounts.sh`'s `devos_tool` makes them the tool's account slots (`<env>_N`, `<alt_env>_N`) and clears them.
   - The watchdog strips them too.
   - So no step of `devos-work.yml` or `devos-review.yml` names a tool's keys.
3. **The planners in their own workflow.**
   - `devos-intake-planner.yml` (new, `workflow_call`) holds the `intake` and `revise` jobs, moved unchanged except
     for their inputs and the generic keys. It is handed only the four secrets its caller passes.
   - In `devos-intake.yml`, `intake-resolve` and `revise-resolve` (new, no AI) name the planner's tool and its secrets
     from main; `intake` and `revise` call the planner workflow with them.
   - Before, the planner jobs named all ten of the four tools' secrets, so their runner held every key.
   - The planner checks that main's config still names the tool it was given; if not, it stops and says to run again.
4. **Two behaviour changes a project can see:**
   - A light review is never handed the deep reviewer's key when its own is missing. Before, `LKEY_1 || KEY_1` did.
   - `intake-publish` and `revise-publish` also run when no planner could be named, so the request or PR is told.
5. **The flaky test:** `progress.test.mjs` (e) accepts any first minute ≥ 1 and checks that the minutes rise, as (b)
   does. `date +%s` counts whole seconds, so a start near a second's end read "2 min" (E86 a1's remote check).
6. **The manual:**
   - `AUTOMATION.md`: the `resolve` step, the `devos-intake.yml` row, a new `devos-intake-planner.yml` row, and the
     rows of `accounts.sh`, `tools.mjs` and `agent-watchdog.sh`;
   - `PRECEDENTS.md`: PR-107, live maximum PR-107;
   - `CHANGELOG.md` under 1.14.0-rc.1;
   - `tools/sources.mjs` lists the new workflow; the manifest has 370 files;
   - `.github/actionlint.yaml` lets the repository's actionlint skip the new call's file, as it does for
     `devos-work.yml` and `devos-review.yml` (it lives under `payload/`). D6 lints an installed project to check the
     call for real.
7. **Tests:**
   - `test/keys-by-name.test.mjs` (new):
     - (a) every AI job's caller names the registry's secrets literally, by the names `resolve` gave its tool;
     - (b) inside, the AI jobs hold the keys only generic and name no tool;
     - (c) with the keys generic, every tool's builder, reviewer and planner calls exactly what the base called
       (`test/agent-calls.mjs --generic` against `test/fixtures/agent-calls.json`, unchanged);
     - (d) `accounts.sh` adopts and clears the generic keys, and the watchdog strips them;
     - (e) `tools.mjs secrets` and the resolve steps, run as written in an installed project;
     - (f) intake and revise call the planner workflow with what it declares, and their publish jobs still run.
   - `test/agent-calls.mjs` takes `--generic`; 7 test files changed where they read the moved jobs or the old key
     lines.

23 files in all (21 changed, 2 new). For a project: the same secret names; `devos upgrade` adds the new workflow and
asks no question.
